## 一、改了哪些文件、为什么

**改动原则：能在现有函数里加一个参数解决的，就不新建分支逻辑。** 没有重写任何原有代码路径。

| 文件 | 动作 | 为什么 |
|---|---|---|
| `video2livephoto.swift` | 改（4 处 + 1 处参数解析 + 1 处文案） | 见下面逐条 |
| `makelivp.py` | 新建 | `.livp` 打包逻辑（ZIP 注释那套） |
| `makelivp.sh` | 新建 | 给人用的一行封装，`./makelivp.sh <图> <mov> <out.livp>` |

| `build.sh` / `livephoto.sh` / `verify.sh` / `mktestvideo.swift` | **一个字没动** | 不需要动，实际也没动（md5 与改前一致，见第八节） |

### `video2livephoto.swift` 逐条改动

1. **`writeJPEG()` → `writePhoto(_:to:format:assetIdentifier:)`**
   - 原来写死 `"public.jpeg"`，现在按格式选 UTType（jpg → `public.jpeg`，heic → `public.heic`）。
   - **Apple MakerNote key 17 的写法一个字没改**，两种格式走同一份 props，不分叉 —— 这是「不要改坏」的关键点。
2. **`GroupResult.jpg` → `GroupResult.photo` + 新增 `photoFormat` 字段**，`convertGroup()` 多一个 `photoFormat: String` 参数。
   - 输出文件名 `\(prefix).\(photoFormat)`。
   - 顺带：开工前把同名 `.jpg` 和 `.heic` **都**删一遍，避免换格式重跑时旧封面残留。
3. **新增参数 `--photo-format jpg|heic`，默认 `"jpg"`。**
   - 只接受这两个值，别的值直接报错退出。**不传时行为与改前完全一致**。
4. **`inspect()` 支持 HEIC**：封面参数由 `jpgPath` 改为 `photoPath`，按扩展名判断走 JPEG 的 Exif 段遍历还是 HEIC 的字节搜索，输出文案跟着变。
5. **`--inspect` 的字节层复核从「仅供参考」升级为「不通过就不通过」。** 这是本次唯一一处**行为加强**：以前字节搜不到不影响退出码，现在算不通过。
   - 依据：改前的 19 项自检日志里这一项本来就是「命中」（`test/verify-raw.log` 第 59 行），所以加强不会误伤，反而能挡住「ImageIO 读到了但字节层面没有」的假通过。

### 新增的 HEIC 相关函数

- `photoUTI(_:)`、`writePhoto(...)`
- `containsBytes(_:_:)`：`[UInt8]` 上没有 `range(of:)`，自己写一个（编译期踩到的坑，见第七节）
- `uuidInHEICBytes(url:uuid:)`：HEIC 的字节层复核

### 2.2 「HEIC 里有 MakerNote tag 17」这件事，证据到哪一步

你要求「Pillow 读不出就用字节搜索 + 结构检查，并写清方法和可信度」。这里给了**三条**，逐条说清能证明什么、不能证明什么。

**证据 1 —— ImageIO 直接读出 key 17（主证据）**

`CGImageSourceCopyPropertiesAtIndex` 拿 `kCGImagePropertyMakerAppleDictionary["17"]`，HEIC 里读出的是完整 UUID，且与 MOV 的 `content.identifier` **逐字符相同**。
这正是 JPG 路径一直在用的同一套读法——ImageIO 自己是会解析 MakerNote 的，它读到了 tag 17，就说明 tag 17 在。
**能证明**：tag 17 存在且值正确。**局限**：这是「库告诉我」而不是「我自己看见」。

**证据 2 —— 整文件字节搜索（辅证）**

HEIF（brand=heic）全文件搜该 UUID 的字节：**只找到 1 处**，在偏移 1500；该偏移前 96 字节里同时有 `Apple`（maker note 头）和 `MM`（MakerNote 的 TIFF 字节序标记）。
**能证明**：UUID 确实写在 maker note 区域里，不是写在别的地方凑数。**局限**：单靠它不能证明「一定挂在 tag 17 这个条目上」。

**证据 3 —— 按结构一层层走进去把 tag 17 取出来（最强，`heic-makernote.py`）**

不靠任何图像库，自己解析字节：

```
HEIF meta → iinf/iloc 拿到 item 清单
  id=8  type=Exif   extents=[(1414, 1538)]        ← 含 UUID 的 item，类型就是 Exif
该 item 数据前 16 字节: 00 00 00 06 | 45 78 69 66 00 00 | 4D 4D 00 2A 00 00
                       ↑到 TIFF 头的偏移=6        "Exif\0\0"    ↑"MM\0*" TIFF 头
TIFF IFD0 偏移 8:  tag 0x8769 (ExifIFD 指针) → 偏移 26
ExifIFD:           tag 0x927C (MakerNote) type=7 count=70 偏移=44
  MakerNote 前 14 字节 = b'Apple iOS\x00\x00\x01MM'   ← exiftool 认的 Apple maker note 头
Apple MakerNote 内部 IFD：条目数=1
  MakerNote tag 17  type=ASCII count=37  value='48D15F56-0218-4FD9-8388-B14FD1970A19'
   （偏移相对 maker note 起点）
== 结论 ==
  按结构取出的 MakerNote tag 17 = '48D15F56-0218-4FD9-8388-B14FD1970A19'
  MOV 里的 content identifier  = '48D15F56-0218-4FD9-8388-B14FD1970A19'
  两者相同 = True
```

**结论可信度**：证据 3 是完整结构证据 —— 从 `iloc` 里拿到 Exif item 的字节区间，经 TIFF IFD0 → ExifIFD → MakerNote → Apple maker note 内层 IFD，落到 tag 17（type=ASCII, count=37 = 36 字符 UUID + NUL）。三条互相独立、结论一致，**可以认为「HEIC 封面里有 MakerNote tag 17 且值与 MOV 一致」这件事已经证实**。
唯一没做的是真机验证「iOS 是否接受我们自己写的这份 HEIC」（本机没有 iPhone）。

## 三、能力 B：`makelivp.py` + `makelivp.sh`

### 3.1 注释结构（严格照给定的规则，没有自创）

```python
comment = "0002"
        + hex32(图片数据起始偏移) + hex32(图片 compressedSize)
        + "0003"
        + hex32(视频数据起始偏移) + hex32(视频 compressedSize)
        + "313030304C495650"          # ASCII "1000LIVP"
```

- `hex32` = 8 位大写十六进制，不足补 0
- 数据起始偏移 = local file header 起点 + 30 + 文件名长度 + **extra 字段长度（从 header 偏移 +28 读，不写死 0）**
- `compressedSize` = 从 local file header 偏移 +18 读 4 字节小端
- 注释长度写到 EOCD 起点 +20（2 字节小端），注释紧跟 22 字节 EOCD 之后

### 3.2 两个「不做就废」的前提，脚本自己断言

1. **条目必须带真实 compressedSize（不能用 data descriptor）** —— 脚本遍历 local header，发现通用标志位 bit 3 被置位、或 compressedSize 为 0，**直接报错退出**，不生成文件。
2. **EOCD 后面必须正好结束、且原来没有注释** —— 不满足就报错，不做「猜着修」。

### 3.3 一个我加的判断：条目用 STORED（不压缩）

MOV / HEIC 本身已经是压缩数据，deflate 省不了多少字节，但 STORED 有个实际好处：**注释里的偏移处就是原始文件本身**，对导入流程最宽容（它要是不解压直接当原文件用也不会错）。所以用 `ZIP_STORED`。

### 3.4 命令与原始输出

```

  [1] 3秒.heic    header@0        data@39        compressedSize=195723
  [2] 3秒.mov     header@195762   data@195800    compressedSize=889878

  0002000000270002FC8B00030002FCD8000D9416313030304C495650
```

注释拆开读：

| 段 | 值 | 含义 |
|---|---|---|
| `[0:4]` | `0002` | 图条目标记 |
| `[4:12]` | `00000027` | 图数据起始偏移 = 39 |
| `[12:20]` | `0002FC8B` | 图 compressedSize = 195723 |
| `[20:24]` | `0003` | 视频条目标记 |
| `[24:32]` | `0002FCD8` | 视频数据起始偏移 = 195800 |
| `[32:40]` | `000D9416` | 视频 compressedSize = 889878 |
| `[40:56]` | `313030304C495650` | ASCII `1000LIVP` |

**顺手做的独立交叉核对**（用 Python 标准库 `zipfile` + 系统 `unzip`，都不是我自己的代码）：

- `zipfile.ZipFile(...).testzip()` → `None`（ZIP 结构完整，手写 EOCD 没把 ZIP 弄坏）
- `zipfile` 给的 `header_offset`（0 和 195762）反推数据偏移 = 39 / 195800，**与注释里的数字一致**
- `unzip -l` 能正常列出两个条目；`unzip -z` 打出的注释与文件里的注释一模一样
- 包内取出的字节 md5 == 原始文件 md5（STORED 直存）

## 四、能力 C：`verify-livp.py`

### 4.1 它到底验什么（不是打 "OK"）

1. 按 `50 4B 03 04` 顺序遍历 local file header，列出每个条目的文件名、数据偏移、压缩大小
   —— **直接用 `from makelivp import scan_local_headers`**，不是另写一套。这样才算真正复现导入流程的读法（算法同源，改一处两边一起改）。
2. 按规则重建期望注释，与文件里实际的注释**逐字符比对**，不一致时打印**第几个字符起不同 + 期望/实际**。
3. 用注释里的偏移 + 大小去文件里切字节，验证：①区间在文件范围内 ②切出的字节与该条目顺序遍历出来的字节 **md5 相同** ③MOV 前 8 字节是合法 box 头且第一个 box 是 `ftyp`，图的前几字节含 `ftyp`（HEIF）或 `FF D8`（JPEG）。
4. 把注释末尾 16 个 hex 解成 ASCII 打印出来，确认是 `1000LIVP`。

任一项不过 → 打印 `[不通过]` → **退出码 1**。

## 五、反向验证：改坏注释必须报错（证明它不是永远说通过）

拿 `3秒-ascii.livp` 复制 4 份，各改坏一个字节，然后跑 `verify-livp.py`：

| 改坏方式 | 退出码 | 报出来的不通过项 |
|---|---|---|
| ① 图数据偏移少 1（hex 末位 `8`→`9`） | **1** | 逐字符比对不一致（第 11 个字符起）+ 切出的字节与条目数据 md5 不同 + 图前几字节不含 ftyp |
| ② 固定尾串改 1 个字符（`1000LIVP`→`1000LIVQ`） | **1** | 逐字符比对不一致（第 55 个字符起）+ 末尾 hex 解出 `'1000LIVQ'` ≠ `'1000LIVP'` |
| ③ 视频压缩大小改 1 位（`1`→`0`） | **1** | 逐字符比对不一致（第 38 个字符起）+ 切出的字节与条目数据 md5 不同 |
| ④ 只把 EOCD 的注释长度字段从 56 改成 55 | **1** | 注释尾与文件尾对不上（差 1 字节）+ 长度 56 vs 55 + 比对到第 55 字符起不同 + hex 解 ASCII 失败（奇数长度） |
| **对照组：未改坏的原文件** | **0** | 20 项全过 |

到此可以确认：**只要注释里任何一个字符不对，或者注释长度字段不对，`verify-livp.py` 都会报错退出**。它不是「永远说通过」。

## 七、踩坑记录（给下一个改这个工具的人）

1. **`[UInt8]` 上没有 `range(of:)`。** 写 HEIC 字节搜索时想找 `Apple` / `MM`，`window.range(of:)` 直接编译不过（`value of type '[UInt8]' has no member 'range'`）。自己写了 `containsBytes(_:_:)`。三行的事，但会卡住第一次编译。

2. **`makelivp.py` 里我把「注释长度上限」写成了「文件总长上限」。** 原写法 `len(data) + len(cb) > 0xFFFF` —— 13 MB 的 `.livp` 必然触发，第一次打包就报错退出。正确判断是**注释本身**不能超过 65535（2 字节字段的上限），跟文件多大无关。**这个错很容易犯，因为它只在包大过 64 KB 时才暴露。**

3. **HEIF 的 `infe` box 自己也是 FullBox，我连着踩两次。** 第一次把 `item_ID` 读早了 4 字节（读出 id=512），第二次把 `item_type` 和 `item_name` 的偏移记反了（把 `hvc1` 当成了名字）。正确布局（ISO 14496-12，v2）：
   `size(4) type(4) version+flags(4) item_ID(2) protection_index(2) item_type(4) item_name(null 结尾，不是长度前缀)`。
   判据：解析完 `iinf`，item 类型应该打印出 `hvc1` / `grid` / `Exif` 这些**说得通的字符串**；打印出一串乱码就是偏移错了，别硬往下走。

4. **HEIC 里 Exif item 的「到 TIFF 头的偏移」是从那 4 字节之后开始算的。** 实测该字段值是 6，而 TIFF 头（`MM\0*`）实际在 item 数据偏移 **10** 处（4 + 6），中间夹着 `Exif\0\0`。一开始按「就从 item 开头算」读，结果 `tiff[:2]` 是 `b'Ef'`，报「不是 TIFF」。

5. **Apple maker note 的内部 IFD 紧跟 14 字节头，没有额外的字节序字段。** 头是 `Apple iOS\0` + `00 01` + `MM`，之后直接就是 `count`（大端 2 字节）。我一开始以为 `MM` 后面还有东西，把 `00 01` 当成字节序标记读，条目数读成 256，打印出一堆天文数字 tag。**看到 tag 数 > 30 基本就是读错位置了**（Apple maker note 正常只有一两个条目）。

6. **Pillow 在本机打开 `.heic` 会挂死**（没有 libheif）。不是报错，是一直不返回，只能靠超时杀掉。所以涉及 HEIC 的自动化脚本不要用 Pillow，用 `heic-makernote.py` 或 ImageIO。

7. **中文条目名会让系统 `unzip` 打出乱码，但扩展名不受影响。** `unzip -l 整段197秒.livp` 打出来的文件名是 `�?�段197�?.heic`（ZIP 里置了 UTF-8 标志位 0x0800，`unzip` 按老编码解），而 Python 的 `zipfile` 读出来完全正常。因为版本号只在名字中间、扩展名是 ASCII，正则 `/\.[a-z]+$/` 照样匹配。**所以这不是故障**，是真机上万一不认时的第一个排查点（对应 `--ascii-names`）。

8. **`verify.sh` 会在开头重跑 `build.sh`**，所以 `bin/video2livephoto` 的 mtime 会变成自检的时间，不要把它当成「我最后一次编译的时间」来推断改动时间。
